## Diagnostics and diagnosis

The persisted diagnostics for `1b982e6d-6778-4c0e-8cab-b82af21fdb4b` show:

- `screenCaptureAccess: true`.
- `sourceKind: display`.
- `framesReceived: 707`, `framesEncoded: 707`, `idleFrames: 1434`,
  `inactiveFrames: 0`.
- Last frame status `Complete` and no native error.
- Source content rect/pixels `2560x1440`; requested/final encoded geometry
  `1920x1080`.
- System audio enabled with 1790 encoded packets at 48 kHz stereo; microphone
  disabled.

This rules out a missing TCC grant and proves that audio was encoded. The
native application path had selected `content.displays.firstObject` as the
display anchor for an application-including ScreenCaptureKit filter. On this
three-display setup the Minecraft window can be on another display, allowing
complete frames and the cursor while the captured surface is black.

## Corrective checkpoint

`native/backends/macos/screen_capture_session.mm` now resolves the largest
visible target window and selects the ScreenCaptureKit display with the largest
global-bounds overlap. The old `firstObject` fallback is retained only when no
visible target window can be resolved. The fix is compiled and the native CTest
suite passes 6/6; a fresh normal-client clip is still required before marking
targeted capture verified.
