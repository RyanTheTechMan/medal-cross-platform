# M3.2 real ScreenCaptureKit → VideoToolbox result

Date: 2026-09-18. Host: macOS 27.2 build 26B5086k, Apple M5 Max, Xcode 27.2 beta SDK/runtime development build. App: signed `Medal.app` (`com.squirrel.medal.medal`); capture owner: signed recorder (`com.squirrel.medal.medal.recorder`). Profile: isolated ignored `artifacts/test-profiles/m3.2-capture-*`.

Manual prerequisite actually performed: the authorized interactive user accepted the macOS capture workflow as presented and explicitly chose the requested source in each system picker. No TCC reset/database edit, security disablement, Medal login, microphone, camera or input-monitoring permission was used.

## Display test

Command shape: launch the signed app executable with `NATIVE_PORT_CAPTURE_SELFTEST_KIND=display`, an isolated absolute `NATIVE_PORT_PROFILE_DIR`, and an in-profile report path. Full non-secret command orchestration is represented by `electron-m3.2-capture-display.log` and the result is `m3.2-capture-display.json`.

- ScreenCaptureKit enumeration completed: 3 displays, 339 windows and 49 applications. Only counts are retained; source labels are not logged.
- Selected source kind was independently reported as `display`.
- Effective encoded size was 1920×802 at a requested 60 fps / 20,000,000 bits/s.
- 446 frames entered VideoToolbox and 446 H.264 frames completed; 0 encode failures.
- `kVTCompressionPropertyKey_UsingHardwareAcceleratedVideoEncoder` returned true after a session created with `RequireHardwareAcceleratedVideoEncoder=true`.
- The stream observed two idle frames and a subsequent `source_resumed` state; idle frames were not encoded as new image content.
- The encoded C++ replay store retained 446 packets, 1,722,764 bytes and 8,070,282,250 ns before requested stop.

## Window test

The same signed actual-client path was rerun with `NATIVE_PORT_CAPTURE_SELFTEST_KIND=window`; see `electron-m3.2-capture-window.log` and `m3.2-capture-window.json`.

- Selected source kind was independently reported as `window`.
- Effective encoded size was 1920×740 at the same requested rate/bitrate.
- 455 frames entered and completed VideoToolbox over 8,064,800,083 ns; 0 encode failures.
- Hardware encoder confirmation remained true while capturing.
- The encoded C++ replay store retained 455 packets and 2,842,395 bytes before requested stop.

## What this proves and does not prove

This is actual signed Electron → recovered IPC/WebSocket → native helper → ScreenCaptureKit → direct CVPixelBuffer → VideoToolbox → encoded C++ replay-store evidence. No raw frame is serialized through Electron. It proves basic display and individual-window selection/capture, hardware H.264 use, requested stop, and one real idle/resume observation.

It does not yet prove source disappearance, minimized/occluded/offscreen behavior, timestamp drift bounds, decoder configuration/keyframe snapshot inspection, AAC, a finalized playable file, long soak/performance targets, permission denial/revocation/regrant, or contentCreate/library playback. Those remain open.
