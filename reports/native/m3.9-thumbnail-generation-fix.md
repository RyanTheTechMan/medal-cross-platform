# M3.9 imported-client thumbnail generation fix

Date: 2026-09-20

## Diagnosis

The Balatro MP4s and database rows were valid, but the imported client could
not load the packaged FFmpeg tools' dynamic libraries. The affected app was
built from an already-relocated `ffmpeg`/`ffprobe` copy whose
`native-port/lib` directory was empty. The loader therefore failed on:

```text
/Applications/Medal.app/Contents/Resources/app/native-port/tools/../lib/libavdevice.62.3.100.dylib
```

Medal still inserted a `thumbnail_path` in SQLite, so the UI correctly reported
“Thumbnail not found” when that file did not exist. This was packaging/tool
closure failure, not a Balatro capture or contentCreate failure.

## Correction

The importer was changed to reject an empty native FFmpeg/ffprobe dependency
closure instead of producing a silently broken app. The development import was
then regenerated from the original Homebrew binaries, copied and relinked all
17 required dylibs under `native-port/lib`, and rebuilt/signed with the stable
development identities. The native helper and client protocol were unchanged.

## Live repair evidence

The updated `/Applications/Medal.app` was launched against the isolated
authenticated profile. The imported client backfilled the two newest Balatro
clips without re-capturing them:

| Clip UUID | Thumbnail | Dimensions |
| --- | --- | --- |
| `9a6851fa-d1c6-4c82-ba45-dfd3b103e115` | present | 640×267 JPEG |
| `e66cdad8-5a75-4fc2-8432-4e3ae8f77935` | present | 640×267 JPEG |

The SQLite rows' existing `thumbnail_path` values now point to real files and
the metadata contains the thumbnail sizes/inodes. The live log records both
`thumbnail ... generated successful style` messages. Earlier loader failures
remain in the profile log as preserved failed evidence.
